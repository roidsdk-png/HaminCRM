# استقرار عملیاتی Hamin CRM

## معماری فعال

- دامنه: `https://crm.haminyar.ir`
- پراکسی و HTTPS: Nginx و Let's Encrypt
- برنامه: کانتینر Docker با نام `hamin-social-crm`
- درگاه داخلی: `127.0.0.1:3010`
- داده پایدار: `/root/socialCRM/data`
- بکاپ‌ها: `/root/socialCRM/backups`
- تنظیمات محرمانه: `/root/socialCRM/.dev.vars`

CRM به SSH یا رمز سرورهای منابع دسترسی ندارد. هر منبع فقط رویدادها را با کلید اختصاصی خودش به `POST /api/v1/events` ارسال می‌کند.

## کنترل سلامت

```bash
cd /root/socialCRM
docker compose ps
curl -fsS https://crm.haminyar.ir/api/health
nginx -t
```

پاسخ سلامت باید شامل `status: ok` و `database: connected` باشد.

## بکاپ خودکار

تایمر `socialcrm-backup.timer` هر روز اجرا می‌شود. بکاپ با SQLite Online Backup ساخته، فشرده، صحت‌سنجی و به مدت ۳۰ روز نگهداری می‌شود.

صفحه `/system` برای مالک سامانه فهرست همین فایل‌های `socialcrm-*.sqlite.gz` را نمایش می‌دهد و ساخت، دانلود و حذف فایل انتخابی را انجام می‌دهد. مسیر `/api/admin/backup` فقط خروجی JSON ادغامی و بدون رمزهای مدیران است؛ برای بکاپ فیزیکی کامل دیتابیس CRM از پنل جدید استفاده کنید. حذف فایل بکاپ، دیتابیس فعال CRM یا بانک‌های برنامه‌های مبدأ را تغییر نمی‌دهد. فایل SQLite فشرده از پنل قابل دانلود است، اما بازیابی فیزیکی آن فقط باید در بازه نگهداری و پس از توقف کانتینر توسط مدیر سرور انجام شود؛ فرم بازیابی JSON در `/access` به‌جای آن عمل نمی‌کند.

سرویس بکاپ داخل کانتینر روی loopback اجرا می‌شود و هیچ پورت عمومی ندارد. `BACKUP_SERVICE_TOKEN` فقط در `.dev.vars` با دسترسی ۶۰۰ نگهداری می‌شود.

```bash
systemctl status socialcrm-backup.timer
systemctl start socialcrm-backup.service
```

برای آزمایش یک بکاپ، آن را در مسیر موقت باز کنید و روی نسخه استخراج‌شده `PRAGMA integrity_check;` اجرا کنید. هیچ‌گاه تست بازیابی را روی دیتابیس فعال انجام ندهید.

## انتشار نسخه جدید

1. از دیتابیس و فایل‌های تنظیمات بکاپ بگیرید.
2. `npm run build` را پیش از انتقال اجرا کنید.
3. در سرور، `docker compose config -q` را اجرا کنید.
4. برنامه را با `docker compose up -d --build` منتشر کنید.
5. تا `healthy` شدن کانتینر صبر کنید و تست سلامت و صفحات داخلی را اجرا کنید.

## الزامات امنیتی

- `.dev.vars` باید دسترسی `600` و پوشه پروژه و داده‌ها دسترسی محدود داشته باشند.
- `ADMIN_PASSWORD` حداقل ۱۲ و `SESSION_SECRET` حداقل ۳۲ کاراکتر باشد.
- کلید هر منبع مستقل است و نباید میان منابع مشترک باشد.
- HSTS، جلوگیری از iframe، `nosniff` و مسدودسازی dotfileها فعال می‌ماند.
- لاگ Docker با حداکثر پنج فایل ۱۰ مگابایتی چرخش دارد.
- تغییر سیستم‌عامل و به‌روزرسانی‌های نیازمند reboot فقط در بازه نگهداری انجام شود.
